## 1. 分层结构（逻辑）

```
┌─────────────────────────────────────────────────────┐
│ 输出层   NDJSON 行输出到 debug 串口（F8, D11）        │
├─────────────────────────────────────────────────────┤
│ 判定层   跟随判定引擎（F12）· 告警逻辑（F13）          │
├─────────────────────────────────────────────────────┤
│ 识别层   厂商库查询(F4) · Apple 识别(F5)              │
│          · Continuity 子类型(F6) · 追踪器特征库(F7)    │
├─────────────────────────────────────────────────────┤
│ 解析层   AD 报文解析器（F3）                          │
├─────────────────────────────────────────────────────┤
│ 观测层   被动监听(F1) · 主动扫描(F2) · GATT 深挖(F10) │
│          观测记录：时间戳 + RSSI + MAC（F9）          │
├─────────────────────────────────────────────────────┤
│ 数据层   RAM 滚动窗口（会话内，F11）· 静态库（出厂内置）│
├─────────────────────────────────────────────────────┤
│ 平台层   ESP-IDF + NimBLE + ESP32-C5                 │
└─────────────────────────────────────────────────────┘
```

数据流：观测层抓包 → 解析层拆 AD → 识别层判厂商/类型 → 数据层入滚动窗口 → 判定层算跟随 → 输出层打印/告警。

## 4. 关键设计点

### 4.1 输出：NDJSON（D11 锁定）
- 一行一个 JSON 对象，`\n` 结尾，无缩进、无多余换行。
- 便于 `idf.py monitor` 直接看，或重定向到文件后被 `jq` / Python 逐行解析。
- **必须在 P2 实现字符串转义**：设备名可能含引号、反斜杠、控制字符，当前 P1 骨架未转义（已知限制）。

### 4.2 滚动窗口（F11）
- 实现即设备表（`main.c` 的 `s_dev`）：会话内 RAM，每设备保留 `first_ms`/`last_ms`/`count`/`rssi_min`/`rssi_max`。
- 键 = (地址类型, MAC)。重启清零（C1 约束）。表满（`MAX_DEVICES=200`）时淘汰最久未见的。

### 4.3 跟随判定（F12/F13）——按 D12 重定义，**P5 已实现初版**
- **D12 决策：不做"是否在移动"的判定。** 因此"跟随"退化为**持续近距存在**。
- **定义缺口（正视）**：无位移信号时，无法区分"某设备在跟踪我"与"某设备恰好一直在我附近"。若对所有设备告警，自控设备（手机/耳机）与固定设备都会命中。
- **本版门控（防误报）**：**只在判为追踪器类（F7，如 apple-findmy）且持续近距时才 `follow=true`**；对普通设备不告警。
- **已实现判定式**（`main.c` `dump_snapshot`，阈值在文件顶部宏）：
  `follow = (tracker 非空) AND (rssi_max ≥ NEAR_RSSI_DBM) AND (life_ms ≥ PERSIST_MS) AND (age_ms ≤ PRESENT_RECENT_MS)`
  默认：近距 −75dBm、持续 60s、在线 15s。输出字段 `follow`（bool）与 `warn`（"possible-follower"）。
- **诚实边界**：输出应理解为"持续近距的可疑**追踪器类**设备提示"，**不是移动跟踪检测**。阈值未标定（O8）。
- 真正的移动检测需位移参考（C5 无 GPS/IMU），属搁置能力（O4）。

### 4.3b 主身份模型（2026-10-15 实测驱动）
- **实测现象**：同一 MAC 可带**多个**厂商标识（例：设备既发 iBeacon 的 0x004C，又发自身厂商 ID）。
- **决策**：每设备保留**一个主身份**，按优先级选取：**真厂商(2) > Apple/0x004C(1) > 无(0)**。
- 理由：0x004C（含 iBeacon 格式）最易被冒用，优先真厂商 ID 可缓解 R2；主身份变更时清空旧 `tracker`。
- 未选"多身份数组"方案（更全但更重）。若日后需完整身份列表，再改。
- 实测验证：`MiCarFE7C` 归到 `co=47 Mew Tel Technology`（真厂商），不再误标 Apple。

### 4.3c 设备身份键与 F14（MAC 轮换）
- **问题**：追踪器（Find My/AirTag）**故意轮换 MAC**，按 MAC 归并会不断产生"新设备"，`life_ms` 无法累积。
- **已实现**：身份键类型化——`key=addr`（按 MAC）或 `key=fmkey`（按 FindMy 载荷公钥前 6 字节）。
- **✅ 实测生效（2026-10-15）**：环境中存在长格式 FindMy 报文（含 22 字节公钥），fmkey 设备 `life_ms` 累积到 ~373 秒。
- **身份拆分已修（双向）**：`upsert` pass 2 跨键类型调和——同一 MAC 已存在但键类型不同时合并；收到公钥时把 addr 条目就地升级为 fmkey 键。避免同设备被拆成 fmkey/addr 两条。
- **遗留**：短格式 FindMy（如 `07ff4c0012020002`）无公钥，在首次带公钥包出现前仍以 MAC 键存在。
- **输出过滤**：快照只打印 `age_ms ≤ 30s` 的设备，摘要行给出 `shown`/`hidden`。

### 4.3d ⚠️ 跟随判定误报 → 已降级（实测，2026-10-15）
- **现象**：一次 ~190 秒会话中，7 台 `apple-findmy` 设备命中"跟随"，几乎全是**用户自己的/身边的普通 Apple 设备**（iPhone/AirPods 等）。
- **根因（[INFERRED, HIGH]）**：**普通 Apple 设备也发 FindMy 类广播**。仅凭 `subtype=FindMy` **无法区分 AirTag 与一台 iPhone**——Apple **故意**使二者不可区分（Find My 隐私设计）。
- **决定（D-R9）**：**F13 告警删除**，`follow`/`warn` 字段移除，改为中性信息项 **`near_persist`**（追踪器类设备持续近距）。**它不声称"被跟踪"**，自己设备在列属正常。
- **可用性提升路径（未做）**：基线白名单法——先把自身设备按 fmkey 建基线，只对"不在基线中的新持续近距 Apple 设备"提示。这是 AirGuard 类工具的做法。

### 4.4 厂商/子类型识别（F4–F7）
- Company ID 表：蓝牙 SIG 分配表，编译期生成 C 数组（O6）。
- Apple 子类型：Continuity 载荷首字节，编码表需权威来源 + 实测校准（O3）。**我给不出可信的具体字节值，必须以实测为准。**
